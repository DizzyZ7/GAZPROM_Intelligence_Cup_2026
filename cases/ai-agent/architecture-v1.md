# ТИИм Pulse — архитектура v1

## Цель
Обнаруживать повторяющиеся некритичные пожелания и проблемы пользователей цифровых продуктов, передавать продуктовым командам проверяемые сигналы без дополнительной ручной аналитики поддержки.

## Данные и границы
Источник: единая тикет-система, текст заявок, вложения/изображения, записи звонков. Хранение в источнике — 1 год. ~40 менеджеров поддержки. Внешние LLM и API недоступны. Внутренние Qwen 3.8 (название из кейса), Qwen-ASR, Qwen-VL. Не предполагаем доступа к исходному коду продуктов или Jira без подтверждения.

## Компоненты
1. **Connector**: инкрементальное чтение тикетов, изменений и вложений, курсор и идемпотентность; только разрешенные поля.
2. **Media processor**: ASR для звонков, VL для скриншотов; оригиналы не копировать без необходимости, вести provenance.
3. **Privacy gateway**: минимизация/маскирование ПДн и секретов, разграничение доступа; исходный тикет остается в разрешенном контуре.
4. **Classifier**: дефект / пожелание / вопрос / сервисный запрос / другое; оценка уверенности, abstain.
5. **Signal aggregator**: дедупликация по продукту, сценарию, намерению и периоду; различать «одинаковая проблема» и «одинаковые слова».
6. **Evidence builder**: карточка сигнала: проблема, влияние, частота, уникальные обращения, тенденция, примеры без ПДн, ссылки на разрешенные источники, неопределенность.
7. **Review & delivery**: согласование человеком, передача в существующий канал продуктовой команды, статусы и защита от повторной отправки.
8. **Feedback & metrics**: подтверждение/отклонение, объединение/разделение кластеров, метрики качества, журнал действий.

Логическое разделение не требует восьми отдельных сервисов. MVP: 3 сервиса — ingestion/media, analysis, review/delivery + общая БД/очередь; далее масштабировать по измеренным узким местам.

## Минимальный поток
ticket event → normalize → ASR/VL при необходимости → redact → classify → match existing signals → aggregate → evidence card → human review → delivery → feedback.

## Безопасность
Текст тикета и вложений — недоверенный ввод, не инструкции агенту. Модель не вызывает инструменты публикации напрямую; только сервис с RBAC и approval. Логи не содержат чувствительные тексты. Применять ограничения доступа по продукту. Восстановление после сбоев через idempotency key и retry с backoff.

## Производительность
Нагрузка не задана. Измерить tickets/day, долю аудио, длительность звонков, объем вложений, p95 задержки и время инференса. Приоритет — пакетная обработка некритичных обращений; не блокировать работу поддержки. Квоты на ASR/VL, ограничение размера вложений, DLQ.

## Открытые вопросы
API и права тикет-системы; целевой канал продуктовых команд; перечень продуктов и матрица доступа; допустимая задержка; хранение производных данных; действующие процессы триажа.
