# Pulse. Поиск новых тем, проверка карточек и очередь владельца

## Что можно показать

1. **Поиск новой темы.** В панели загрузите обращения и включите «Искать новые темы (эксперимент)». Прежние правила создают карточки по известным сценариям. Для обращений с категорией `unknown` Pulse сравнивает символьные признаки внутри одного продукта и предлагает карточку при совпадении минимум двух обращений. Карточка получает сценарий `new_topic`, метод `experimental_char_tfidf` и статус ожидания проверки.
2. **Исправление карточки.** Откройте карточку и сравните обезличенные фрагменты с идентификаторами и датами. Кнопка «Это другая проблема» исключает выбранное обращение из открытой карточки. Требуется основание. Событие сохраняется в истории, а повторный импорт не возвращает источник в эту карточку. Подтверждение требует минимум двух источников. Если остался один, можно отклонить карточку или дождаться новых подтверждающих обращений.
3. **Очередь владельца.** При подтверждении аналитиком карточка появляется в разделе «Очередь владельца продукта». Владелец открывает карточку и выбирает «Взято в работу», «Тема уже известна» или «Нужно уточнение», затем указывает основание. Pulse сохраняет момент передачи и момент решения. Если у всех источников есть исходные даты, очередь показывает интервал от первого обращения до решения.

## Локальная демонстрация

Из корня репозитория в PowerShell:

```powershell
cd cases/ai-agent/mvp
python -m pip install -r requirements-api.txt
$env:PULSE_DB = "pulse-flow-demo.sqlite3"
$env:PULSE_REVIEW_TOKEN = "pulse-demo-local"
python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

Откройте `http://127.0.0.1:8000/dashboard`, введите токен и подключитесь. Для повторяемого сценария используйте новую SQLite-базу. Вставьте массив ниже, включите экспериментальный режим и нажмите «Обработать».

```json
[
  {"id":"act-1","product":"Кабинет","text":"Не удаётся выгрузить акт сверки по расчётам","occurred_at":"2026-11-01T09:00:00+03:00"},
  {"id":"act-2","product":"Кабинет","text":"Не удаётся выгрузить акт сверки по расчёту","occurred_at":"2026-11-02T09:00:00+03:00"},
  {"id":"act-3","product":"Кабинет","text":"Не удаётся выгрузить акт сверки по расчётам!","occurred_at":"2026-11-03T09:00:00+03:00"},
  {"id":"act-other","product":"Другой продукт","text":"Не удаётся выгрузить акт сверки по расчётам"}
]
```

Ожидается одна карточка с тремя источниками из «Кабинета». В учебном сценарии предположите, что аналитик сверил первый источник в системе поддержки и обнаружил отдельную проблему. Исключите `act-1`, повторите импорт и проверьте, что осталось два источника. Подтвердите карточку и запишите решение владельца. Исходное время первого оставшегося обращения должно быть `2026-11-02T06:00:00+00:00`. Этот набор проверяет механику и изоляцию продуктов. Сходство формулировок в нём намеренно высокое.

## Карта кода и контракт API

| Компонент | Назначение |
| --- | --- |
| `mvp/service.py` | Накопительный импорт. При `experimental` к сигналам правил добавляются кластеры из неизвестных обращений. Символьный TF‑IDF с n-граммами 3–5, порог 0,70, группировка complete-link. |
| `mvp/benchmark/engine.py` | Отдельный параметр `include_unknown` допускает сравнение внутри продукта. Бенчмарк может сравнивать пары, где неизвестен один или оба участника. Рабочее демо подаёт в этот алгоритм только неизвестные обращения, чтобы сохранить отдельно карточки правил. |
| `mvp/store.py`, `mvp/evidence.py` | SQLite и чтение карточек. Новые таблицы `ticket_dates`, `excluded_sources`, `product_queue` создаются при открытии БД. Исключение, подтверждение с постановкой в очередь и запись решения выполняются в отдельных атомарных транзакциях. |
| `mvp/api.py`, `mvp/dashboard.*` | Управление импортом, просмотр фрагментов, исключение источника и решение владельца. Все маршруты с данными требуют `X-Review-Token`. |
| `mvp/compare_unknown_candidates.py` | Сравнение TF-IDF и опционально Ollama с одним бюджетом ложных совпадений, фиксация порога на validation. |
| `mvp/tests/test_product_flow.py` | Сквозная проверка хранения, защиты от возврата исключённого источника, границы продукта и жизненного цикла карточки. |

- `POST /imports` принимает `{"tickets":[...],"mode":"experimental"}`. Без поля `mode` действует `rules`. Необязательный `occurred_at` принимает ISO 8601 с часовым поясом, нормализуется в UTC. Дату можно добавить при повторном импорте. Конфликт уже сохранённых дат откатывает пакет.
- `GET /signals/{id}` возвращает `sources` с `ticket_id`, `excerpt` и `occurred_at`. Если запись источника недоступна, поля фрагмента и даты могут быть пустыми.
- `POST /signals/{id}/exclude` принимает `{"ticket_id":"act-1","reason":"Другая причина сбоя"}`. История доступна через `GET /signals/{id}/timeline`.
- `POST /signals/{id}/review` с `{"action":"approved","reason":"Подтверждена общая проблема"}` ставит карточку в очередь. Отклонённая карточка в очередь не попадает.
- `GET /product-queue` возвращает момент передачи, исходную дату первого источника на момент передачи и решение. `POST /product-queue/{id}/decision` принимает `{"decision":"known","reason":"Есть задача в бэклоге"}`. Варианты решения: `in_progress`, `known`, `needs_clarification`. Повторная запись решения возвращает 409.

Для базы, созданной до изменений, прежние карточки и решения читаются. Ранее подтверждённые карточки автоматически в очередь не переносятся. Новые источники могут дополнять подтверждённую карточку, а дата первого обращения в очереди фиксируется на момент передачи. Общий токен обслуживает обе роли в локальном демо. Промышленное разграничение доступа и доставка в корпоративный трекер потребуют отдельной интеграции.

Символьный поиск в панели подбирает веса по накопленным неизвестным обращениям. Офлайн-бенчмарк подбирает веса по development. Поэтому показатели ниже относятся к эксперименту, а не к качеству рабочего импорта. Сравнение пар имеет квадратичную стоимость и ограничено лимитом бенчмарка. Прототип предназначен для небольшого синтетического потока. Маскирование унаследовано от текущего прототипа и охватывает телефон и email.

## Локальный результат

На синтетической выборке validation из 100 обращений было 71 эталонное совпадение. Строгий фильтр отсёк все 71. Расширенный фильтр допустил все 71 и ещё 1554 нерелевантные пары. Порог выбирался из сетки 0,05–0,95. Среди порогов с максимум 10 ложными совпадениями выбирали тот, который нашёл больше настоящих повторов. При равенстве выбирали меньше ошибок, затем более высокий порог.

| Метод | Порог | Найдено повторов из 71 | Ложные совпадения | F1 группировки |
| --- | ---: | ---: | ---: | ---: |
| Смешанный TF-IDF со строгим фильтром | 0,95 | 0 | 0 | 0,00 |
| Смешанный TF-IDF с расширенным фильтром | 0,65 | 4 | 10 | 0,10 |
| Словный TF-IDF с расширенным фильтром | 0,75 | 2 | 1 | 0,05 |
| Символьный TF-IDF с расширенным фильтром | 0,70 | 4 | 4 | 0,10 |

Символьный вариант нашёл столько же повторов, сколько смешанный, и предложил на шесть ложных совпадений меньше. Это сравнение на validation. Условие перехода к holdout было строже: больше настоящих повторов при том же предельном бюджете ошибок. Ни один вариант его не выполнил. Holdout не запускался, а сохранённый отчёт исходного бенчмарка остался историческим результатом. Эмбеддинги пока не проверены.

## Запуск для коллеги

В PowerShell из корня репозитория:

```powershell
cd cases/ai-agent/mvp
python -X utf8 compare_unknown_candidates.py
```

Если Git на Windows преобразовал LF в CRLF, проверка контрольных сумм остановит запуск. В таком случае воспроизведите набор в отдельной папке и передайте её скрипту. Указанная папка должна отсутствовать перед генерацией.

```powershell
python -X utf8 -m dataset generate --size 500 --seed 20261105 --output pulse-validation-lf
python -X utf8 compare_unknown_candidates.py --dataset pulse-validation-lf
```

Для проверки эмбеддингов запустите Ollama на локальном компьютере и посмотрите имя установленной модели через `ollama list`. Нужна модель, поддерживающая эмбеддинги через `/api/embed`. Подставьте её имя в команду.

```powershell
python -X utf8 compare_unknown_candidates.py --ollama-model 'ИМЯ-МОДЕЛИ' --check-holdout
```

Если использовалась папка `pulse-validation-lf`, добавьте `--dataset pulse-validation-lf` и к команде Ollama. Скрипт использует локальный адаптер репозитория и записывает имя и digest модели в JSON. Отправьте команде JSON с результатами. Если ни один новый метод не обошёл смешанный TF-IDF по количеству найденных повторов в рамках бюджета, в отчёте будет `no_validation_winner`. Если обошёл, скрипт сравнит лидера и базовый вариант на holdout с уже выбранными порогами. Порог по holdout не подбирайте.

При проверке Ollama посмотрите найденные и ложные пары, F1 группировки и долю пропусков. Бюджет в 10 ошибок относится к этому эксперименту. Рабочий лимит нагрузки на аналитика нужно определить на пилоте. Панель использует локальный символьный режим, а флаг Ollama запускает отдельное сравнение. Для смены метода в рабочем импорте сначала подтвердите качество на отложенной выборке и определите, как сохранять идентичность карточек при смене модели.
