# P3. Контекст обращения и проверка на новых семействах

Аналитик импортирует сообщения в Pulse и получает кандидатов на проверку. P2 выявил системный отказ классификации на новых семействах. Действующая группировка по трем полям также может объединять разные симптомы одного сценария. В этой итерации задача состоит в извлечении контекста, консервативной группировке и измерении результата на новой контрольной выборке.

## Контракт решения

- Контекстный разбор выделяет категорию, сценарий, операцию и наблюдаемый симптом. Неполный или противоречивый контекст сохраняется как отказ от группировки с кодом причины.
- В кандидат попадают повторные `bug` и `feature_request` с одинаковым полным контекстом в одном продукте. Эмбеддинги дополняют проверку контекста через complete-link.
- API и CLI принимают явный режим `context`. Явный выбор сохраняет совместимость существующих интеграций и дает контролируемое переключение базы с рассмотренными сигналами. Обычная классификация P2 остается доступной для исторического сравнения.
- Накопительный импорт атомарен. Однозначное совместимое расширение сохраняет ID и решение аналитика. Пересечение нескольких групп, изменение контекста или исчезновение прежнего источника блокируют автоматическую запись. Применение ручного merge/split с отдельным журналом составляет следующую часть P3.
- Транспорт Ollama, модели и авторизация сохраняют действующие границы локального контура. Новый код использует стандартную библиотеку Python и существующие интерфейсы.

Выбран детерминированный разбор наблюдаемых признаков. Он позволяет выделять новые сочетания сценария и симптома, сохраняет объяснение и работает в текущем локальном MVP. Обучаемый классификатор потребовал бы новых размеченных примеров и отдельной калибровки отказа. Семантический провайдер остается дополнительной проверкой после разрешения контекста.

## Выполнение

1. Добавить контекстный классификатор и общий конвейер для контекстного и embedding-режима. Проверить отрицание, смешанные сообщения, разные симптомы одного сценария, недостаточный контекст и продуктовую изоляцию.
2. Подключить API и CLI. Проверить два накопительных пакета, идемпотентность, однозначный рост прежнего сигнала и атомарный отказ при конфликте состава.
3. Сохранить новый набор с семействами, подготовленными отдельно от кода. До первого чтения текстов и меток зафиксировать исходники, состав методов и SHA-256 манифеста. Применить старый и новый анализаторы к одному входу. Сопоставить предсказания с эталонами после вычисления обоих результатов.
4. Сохранить классификационные и pairwise-метрики, коды отказов и ошибки. Сравнивать macro F1 категории и pairwise F1 с прежним анализом на том же новом наборе. Ненулевая полнота, отсутствие межпродуктовых пар и отсутствие группировки входов с явными инструкциями служат локальными критериями этой проверки. Отдельно показать ложные объединения и пропуски.
5. Провести независимый обзор кода, полные регрессионные проверки и CI. Сохранить исходный benchmark P2 и его проверяемость. Оформить PR и объединить после успешных проверок.
