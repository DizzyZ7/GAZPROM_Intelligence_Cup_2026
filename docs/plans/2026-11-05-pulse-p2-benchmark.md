# План P2: независимая оценка методов ТИИм Pulse

Основание: приоритет P2 из технического аудита, требования к воспроизводимости, изоляции holdout и честному сравнению трех методов. P0/P1 объединены в main, исходная версия `a390b3d`.

## Результат и границы

Отдельный офлайн-пакет `mvp/benchmark/` сравнивает Rules, смешанный TF-IDF word/character n-grams и локальные эмбеддинги через существующий EmbeddingProvider. Рабочий API и SQLite не изменяются. Новые runtime-зависимости не требуются.

Во всех трех вариантах используется действующий классификатор: категория и сценарий вычисляются из текста, а не берутся из gold. Это контролируемое сравнение поиска повторов и кластеризации с одинаковой классификацией. Отдельная матрица ошибок и доля отказов покажут ограничение общего классификатора. Оно не скрывается за показателями сходства. Обучение нового классификатора относится к последующим улучшениям.

TF-IDF: word 1–2, char внутри границ слова 3–5; sublinear TF, сглаженный IDF, нормирование двух ветвей и равные веса. Словарь и IDF строятся только по development. Порог выбирается на validation по pairwise F1 итоговой complete-link кластеризации; при равенстве предпочтение меньшему числу ложных объединений, затем большему порогу. Сетка 0,05–0,95 с шагом 0,05 фиксируется до оценки.

Оценки классификации, порогового поиска похожих пар, top-5 поиска и итоговых кластеров сохраняются отдельно. Все пары исходных обращений участвуют в знаменателях; ошибки категории и отказ от решения не исключаются из расчета полноты. Одно обращение, повторные события и многопроблемные записи не становятся дополнительными независимыми источниками.

Параметры, состояние TF-IDF, отпечатки набора и исходных файлов сохраняются до holdout. Калибровка читает только development/validation. CLI финальной оценки не принимает порогов и читает holdout только после проверки зафиксированного протокола. Повторная оценка того же протокола блокируется квитанцией использования; проверка сохраненного отчета не запускает модель повторно.

Модель C без провайдера имеет статус «не проверено» и пустые числовые результаты. Неуспешный инференс отмечается отдельно; подмена демонстрационными векторами не допускается. Для Ollama фиксируются имя и digest реально доступной локальной модели; интерфейс корпоративного адаптера не предполагается совместимым с Ollama.

## Задачи и критерии приемки

1. `benchmark/metrics.py`, `tests/test_benchmark_metrics.py`: ручные эталоны confusion matrix, precision/recall/F1, pairwise метрик, false merges/missed repeats и top-k. Пустые знаменатели явно описаны.
2. `benchmark/tfidf.py`, `benchmark/engine.py`, `tests/test_benchmark_engine.py`: независимый TF-IDF, запрет fit на новых документах, проверка границ продукта/категории/сценария, отсутствие цепочного объединения, одинаковый Rules baseline, проверка векторов и лимит числа пар.
3. `benchmark/protocol.py`, `benchmark/reports.py`, `benchmark/__main__.py`, `tests/test_benchmark_protocol.py`: разделенные tune/evaluate/verify; контрольные суммы, отсутствие чтения holdout при калибровке, запрет подмены состояния и повторной оценки, ошибки без раскрытия текста, отчеты JSON/CSV/Markdown и примеры ошибок.
4. Регрессия всех тестов; Ruff, Bandit, проверка зависимостей и секретов; независимая инженерная проверка и исправление существенных замечаний через RED → GREEN.
5. После фиксации кода: реальная калибровка на validation, однократная финальная оценка holdout, сохранение отчета с фактическими метриками и измерениями времени/памяти. Время измеряется отдельно от качества; traced Python memory не выдается за всю память системы/GPU.
6. Обновление русской документации и CI; commit/PR, успешный CI и объединение без обхода защиты ветки.

## Пограничные проверки

Gold в признаках; неизвестные категории; singleton и многопроблемный текст; zero/nonfinite/inconsistent embeddings; одинаковые слова разных продуктов; complete-link цепочка A–B–C; поврежденное состояние TF-IDF и манифест; изменение порога после фиксации; отсутствующая модель; невалидный выход модели; повторный holdout; большой пакет с квадратичным числом пар.

## Ограничения вывода

Синтетические семейства не являются корпусом реальных обращений; экспертная проверка еще ожидается. Нельзя заявлять превосходство на корпоративном потоке, качество неустановленной модели, причинность ошибок продукта или промышленную производительность по одному локальному запуску. Ограничение размера benchmark защищает память; оценка крупных корпусов требует отдельного протокола и масштабируемого поиска кандидатов.
